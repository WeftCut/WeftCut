# Content downloads are a main-owned, resumable queue

App-managed content (ADR 0039/0043/0055) is downloaded by a queue that lives in the Electron main process and resumes from the bytes already on disk. The renderer's Settings row is a projection of that queue, never its owner. This replaces the first cut, where the byte stream ran in main but the multi-item sequencing was a renderer closure, every attempt started from byte zero, and the partial directory was wiped at boot.

The reason is the third catalog slice: a 2.5 GB model over a consumer connection cannot be treated like an 8 MB runtime. Any drop, stall, dialog close, or quit that costs the whole transfer makes the feature unusable, and a UI that renders from its own local phase rather than from main state tells the user the download stopped when it did not.

## Consequences

- One queue, in main (`src/main/contentQueue.ts`), runs items one at a time in enqueue order. `content:enqueue` returns at once with a snapshot; every change is broadcast whole on `evt:content:queue`, so a freshly mounted row needs no reconciliation. Main filters out installed items itself; the renderer's `missing` list is no longer the only guard.
- A partial (`cache/content-partial/<id>.part`) is never discarded for a transfer failure. A sidecar `<id>.part.json` records the artifact's url, sha256, byte count, and version; when it matches the current catalog entry, the next attempt sends `Range: bytes=<size>-` and re-hashes the prefix from disk before appending (sha256 state is not serializable, so the prefix is read once more). A `200` to a Range request restarts from zero; a `416` discards the partial and refetches whole; a partial the sidecar does not vouch for is junk. Only a failed verification or a post-verify install failure removes a partial.
- Retries resume: the 3-attempt cap stays, with a 1 s / 4 s backoff, and a 45 s stall watchdog aborts a silent connection and counts as one transfer failure. Cancel keeps the partial, so cancel is pause; `content:remove` deletes the partial along with the install.
- The boot sweep keeps partials the catalog still vouches for and deletes everything else (orphans, retired entries, oversize files). Partials stay under `cache/`, so the data-root migration still never copies them; losing a partial on a data-root move is accepted.
- The ordered pending list is persisted to `cache/content-queue.json` on every membership change and re-enqueued at boot, so a quit mid-download resumes at next launch without asking. `before-quit` aborts the in-flight fetch (the file handle closes at a chunk boundary) without touching the persisted list.
- The Settings row derives everything from `content:list` plus the queue snapshot: Cancel while anything is pending, with each pending item's state and bytes beneath it; Download / Re-download / Retry when something is missing; the managed caption only when every covered row is installed on disk. An `error` entry lingers in the snapshot until re-enqueued or cancelled, so Retry can name the cause.
- Progress outside Settings is the existing LogBus Job op per item; its throttled Progress messages carry the percentage, which is what the status bar shows. No toast, no new pill.
- Verified on this machine through Electron `net.fetch`: both Hugging Face `resolve` URLs and GitHub release assets answer a Range request with `206` after their redirect, which is what makes the resume path real rather than assumed.
